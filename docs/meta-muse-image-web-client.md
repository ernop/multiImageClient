# Meta Muse Image Web Client: Product and Engineering Handoff

## Purpose

Add Meta's Muse Image model to MultiImageClient as a consumer-session generator named `meta-web`.

Meta does not currently publish a general-purpose Muse Image developer API. Muse Image is available through Meta AI product surfaces, while Meta's separate Model API exposes Muse Spark rather than Muse Image. Therefore, this integration must automate the consumer `meta.ai` experience and must remain clearly distinct from any future official `meta-api` provider.

The intended user experience is:

- Run Muse Image from the command line with `--meta-web`.
- Include it in generic showcases with `--showcase --gens meta-web`.
- Expose it as an optional generator in the local `--ui` interface.
- Save raw returned image bytes through the existing `ImageManager` pipeline.
- Create normal annotations, JSON logs, mirrors, and combined contact sheets.
- Use the user's own Meta AI consumer session, with no claim that the integration is official or stable.

## Product naming

- `meta-web`: consumer `meta.ai` browser-session integration.
- `MetaWeb*`: internal C# type prefix.
- Reserve `meta-api` for a future official Muse Image API, if Meta releases one.

This follows the existing `grok-api` versus `grok-web` distinction.

## Current implementation

The repository currently contains the following scaffold:

- `MultiImageClient/MetaWebCookieLoader.cs`
  - Reads a raw Cookie header, DevTools cookie export, Netscape `cookies.txt`, or simple `name=value` lines.
  - Filters cookies for `meta.ai`.
- `MultiImageClient/MetaWebClient.cs`
  - Currently attempts image generation through an old persisted-query GraphQL mutation.
  - Downloads media URLs and maps failures to `MetaWebException`.
- `MultiImageClient/ImageGenerators/MetaWebImagineGenerator.cs`
  - Implements `IImageGenerator`.
  - Maps generated bytes to `TaskProcessResult`.
  - Uses the existing image-saving and contact-sheet pipeline.
- `MultiImageClient/Workflows/MetaWebWorkflow.cs`
  - Implements the `--meta-web` batch workflow.
- Supporting wiring:
  - `ImageGeneratorApiType.MetaWebImagine`
  - Settings and settings-template fields
  - CLI parsing and help
  - Provider validation
  - Run statistics
  - `--showcase --gens meta-web`
  - Documentation in `AGENTS.md`

The solution builds, but the generation transport is not production-ready.

## Critical protocol finding

The old HTTP GraphQL image-generation path is retired.

The current community reference implementation, `mir-ashiq/metaai-api`, states that Meta migrated chat and image generation to a custom Datagram WebSocket protocol called DGW. The browser creates integrity-checked DGW messages. The reference project therefore uses browser automation for generation and retains HTTP GraphQL only for operations such as fetching media for a known card.

Consequences:

- Updating a persisted-query `doc_id` is not sufficient.
- The current `MetaWebClient.GenerateImageAsync()` request is expected to fail.
- The old image-generation variables, including orientation and requested image count, cannot be treated as supported.
- Reimplementing DGW directly is not currently practical without live protocol captures and an understanding of the integrity mechanism.
- Browser automation is the recommended transport.

## Review findings in the current scaffold

### Blocking

1. `MetaWebClient.GenerateImageAsync()` calls the retired HTTP GraphQL generation mutation.
2. The CLI and documentation imply that replacing a stale `doc_id` can restore generation. Current evidence says the transport itself changed.

### High priority

1. Media polling uses obsolete assumptions:
   - old poll `doc_id`;
   - guessed friendly name;
   - guessed `mediaSetId` variables.
2. Polling catches all `MetaWebException` instances and can wait for the full timeout after a deterministic failure.
3. URL extraction accepts broad CDN matches and could select an avatar, thumbnail, or other unrelated Meta media.
4. Cookie guidance is inaccurate:
   - current working browser references use `datr` and `ecto_1_sess`;
   - `abra_sess` is optional;
   - the present documentation emphasizes `abra_sess`.

### Medium priority

1. `orientation` and `numImages` are exposed despite not being confirmed on the current browser/DGW path.
2. `MetaWebClient.FromCookieFile()` does not pass the poll-doc-id setting.
3. There are no live integration tests.
4. The local web UI does not currently expose `meta-web`.

## Recommended architecture

Replace the generation portion of `MetaWebClient` with a Playwright-based browser client.

### Browser lifecycle

- Use Playwright for .NET.
- Prefer a dedicated persistent Chromium profile for Meta AI.
- Support a headed first-run/login mode.
- Optionally support cookie injection from `MetaWebCookiePath`.
- Keep one browser context alive for the lifetime of a CLI workflow or local UI server.
- Serialize Meta operations inside the shared client with a `SemaphoreSlim`.
- Do not create a new browser for each prompt or each UI job.
- Close the context and browser cleanly when the workflow or server stops.

### Authentication

Preferred order:

1. Dedicated persistent browser profile with a one-time interactive login.
2. Fresh cookie export containing:
   - `datr`;
   - `ecto_1_sess`;
   - optional `abra_sess`;
   - preferably the complete `meta.ai` cookie jar.

Cookies are credentials:

- Never paste them into chat.
- Never log cookie values.
- Never commit the cookie file or browser profile.
- Store them outside the repository or in an ignored local path.
- Error messages may include the cookie-file path but not its contents.

Suggested local path:

`~/.config/multi-image-client/meta-ai-cookies.txt`

### Generation flow

For each prompt:

1. Navigate to or reuse the Meta AI chat page.
2. Confirm the session is authenticated and that the composer is available.
3. Snapshot existing generated-media URLs or DOM identities.
4. Enter the prompt through the real page.
5. Submit it and let Meta's own JavaScript create the DGW messages.
6. Wait for newly added generated-image elements.
7. Ignore media that existed before submission.
8. Filter known UI assets, avatars, emojis, and thumbnails.
9. Prefer the highest-resolution source exposed by `srcset`, links, or the image viewer.
10. Wait for generation to settle before returning.
11. Download the selected bytes with the authenticated browser context or HTTP client.
12. Validate that each response is an image by HTTP content type and file signature.
13. Return the original bytes unchanged.

### Diagnostics

Add opt-in session diagnostics similar to `grok-web` capture:

- timestamps and state transitions;
- current page URL;
- sanitized DOM snapshots around generated cards;
- newly observed media URLs;
- HTTP status and content type for downloads;
- screenshots on timeout or authentication failure;
- no cookies, authorization headers, access tokens, or full local profile contents.

### Initial feature scope

Ship the first reliable version with:

- text-to-image only;
- one submitted prompt at a time per Meta browser session;
- output count determined by what Meta returns;
- no claimed orientation control;
- no claimed exact image-count control;
- no image upload/editing until separately captured and validated;
- headed mode available for troubleshooting.

## Local web UI integration

`meta-web` is not currently exposed in `--ui`.

The current UI generator keys are:

- `gpt2`
- `grok-web`
- `grok-api`
- `grok-api-pro`

The frontend dynamically renders the list returned by `/api/config`, so Meta integration is mostly server-side.

Required UI work:

1. Add `UiJobRunner.KeyMetaWeb = "meta-web"`.
2. Add a Meta descriptor to `/api/config`.
3. Report availability from the configured browser profile or cookie path.
4. Keep the Meta browser client as a shared, long-lived service.
5. Route `meta-web` jobs through that shared client.
6. Ensure concurrency is enforced by the shared client, not only by per-generator semaphores.
7. Dispose the browser during application shutdown.
8. Initially reject jobs with an attached input image with a clear "Meta editing is not implemented" result.
9. Do not enable `meta-web` by default until a live smoke test succeeds.

The browser displaying the local UI cannot directly reuse the user's Meta cookies through frontend JavaScript because of origin, cookie, and browser security boundaries. The local server needs its own Playwright-controlled Meta session.

## Configuration changes for the browser implementation

Recommended settings:

- `MetaWebCookiePath`
- `MetaWebBrowserProfilePath`
- `MetaWebHeaded`
- `MetaWebBrowserExecutablePath` (optional)
- `MetaWebTimeoutSeconds`
- `MetaWebCaptureSessions`

Remove or deprecate once browser generation replaces GraphQL:

- `MetaWebImageDocId`
- `MetaWebPollMediaDocId`
- `MetaWebGraphqlEndpoint`
- `--meta-web-doc-id`

Do not preserve obsolete configuration merely for compatibility unless a known working operation still uses it.

## Validation plan

### Automated checks

- Unit-test cookie parsing for:
  - raw headers;
  - Netscape files;
  - DevTools rows;
  - missing `datr`;
  - missing `ecto_1_sess`.
- Unit-test media candidate filtering with representative DOM/URL fixtures.
- Unit-test image signature and content-type validation.
- Verify `dotnet build MultiImageClient.sln`.
- Run lints on edited files.

### Manual smoke test

1. Create a fresh dedicated Meta AI browser profile or cookie export.
2. Confirm Meta AI image generation works manually in the same region/account.
3. Run one short text-to-image prompt in headed mode.
4. Confirm only newly generated images are captured.
5. Confirm raw bytes are saved verbatim.
6. Confirm annotations and JSON logs are created.
7. Run two prompts sequentially and verify no prior result leaks into the second prompt.
8. Start `--ui`, select only `meta-web`, and run a prompt.
9. Run a fan-out job with `gpt2` and `meta-web`.
10. Confirm simultaneous UI jobs serialize Meta use without corrupting prompts.
11. Test expired cookies and verify the error clearly requests reauthentication.
12. Test headless mode only after headed mode is reliable.

## Operational and product caveats

- This integration is unofficial and may violate or be restricted by Meta's terms, rate limits, or anti-automation controls.
- It may break whenever Meta changes its page, selectors, authentication, or DGW behavior.
- Consumer subscription access does not imply an API service-level agreement or automation entitlement.
- Cost is represented as `0m` because there is no metered API price, not because Meta AI subscriptions are necessarily free.
- Generated images may contain Meta provenance or watermarking.
- Region and account eligibility can affect availability.
- Avoid aggressive concurrency and retries.

## Definition of ready

The feature is ready only when all of the following are true:

- No retired GraphQL generation mutation is used.
- A fresh authenticated session completes a real Muse Image generation.
- The generated image is downloaded and saved through `ImageManager`.
- Previous-page or unrelated CDN images are not returned.
- Authentication and timeout failures are actionable.
- Cookies are never exposed in logs.
- The CLI workflow succeeds.
- The local UI path succeeds.
- The solution builds cleanly.
- Documentation accurately states the browser-automation limitations.

## Immediate next action

Implement the Playwright-based shared browser client, then validate it using a fresh local Meta session. Cookies or a dedicated profile are needed for the live test, but not for writing the initial browser plumbing.
